# 姓名对应现状（2026-10-21）

2026-10-21 后续更正：案例任务 `fe0ec886100e4a08877722bbf00be66b` 后来写入了带时间范围的显式人物标注。README 截图是这条任务在 0:08 的本地结果，双 C 为 XILI 与 AIJING。新导入的视频不会自动得到这些姓名。跨镜头身份仍未完成，这条片子里群舞、双人署名和难以分辨的画面仍有未命名的 C 位时间。下面的段落保留当时的检查记录。

用户要求的是上传视频后由 Agent 自动取画面、检索来源、逐人建立姓名对应并批量标注，用户不必逐个确认，也不是只列出团员名单。这个目标仍未完成。

本轮检查发现，旧“智能识别”模块把轨迹按出现频率、C 位时长等排序，再依次分配名单中的名字。0.7 / 0.95 等数字由该排序逻辑产生，没有身份准确率依据。名单完整、网页出现九个名字，均不能证明人物识别成功。NEON 的一个旧任务保存了九条这类记录；另一个当前观看任务没有姓名对应。

该自动分配入口已停用。`POST /api/jobs/{id}/auto-identify` 返回 409 和 `name_evidence_required`，不更改轨迹或姓名。历史 `auto_identified` 记录保留在原始数据中便于追溯，但不再进入人物标签和姓名计时；不能把它们转换成 `user_confirmed`。旧猜名缓存也不会自动恢复为已确认姓名。JSON 导出的原始 `job.labels` 是历史数据，不是已验证名单，应以 `name_status`、统计行的 `named` 和证据类型判断。

`GET /api/jobs/{id}` 返回 `name_status`，区分来源名单数量、有依据标注的姓名数量、轨迹数量与旧版无依据标签数量。有依据标注的姓名数量不等于已独立验证的真实成员人数。带明确人物标注来源和时间范围的 Agent 回填继续通过 `/annotations` 接口处理，具体协议见 [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md)。字幕演唱者和团员名单不能直接作为画面人物姓名。

本轮运行环境中的 Agent 不能依据人脸或外貌识别、比对真实姓名，也不能把同一识别操作改成搜图后执行。它可以读取明确指向人物的姓名文字、核对来源标注并回填。这是该 Agent 的使用边界，不是宣称技术上不存在人物识别方案。不能将此支持范围写成“任意视频全自动认名已实现”。

先前 README、优化报告中关于“识别率 77.8% / 90%”“全部功能通过”“5× 实时”等声明没有完成相应验证，不作为验收结果。UI 恢复、模型可启动和真实姓名正确对应是不同的验证项。
